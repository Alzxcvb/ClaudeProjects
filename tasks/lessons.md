## 2026-05-20 — CTA must match the live offer end-to-end
**Mistake:** Drafted the Hi I'm Alex launch post promising a "free 15-minute fit call," but the actual landing page (hiimalex.ai) only offers a paid $200 90-min call. Shipped a free→paid funnel mismatch + a double CTA (free call AND $200 Quick Start at once). I'd flagged the final CTA-line mismatch but left the "free" promise in the body.
**Correction:** Alex pointed out the link goes to the $200 paid call and asked why it wasn't a 10/10.
**Rule:** Before finalizing marketing copy, confirm the exact bookable offer (price/duration/free-vs-paid, the event that actually exists in Calendly/Stripe) and make EVERY mention in the draft consistent — not just the link line. One next-action per CTA; don't stack free + paid. Name the deliverable ("$200, leave with Claude running"), not "discovery call."

## 2026-06-03 — "Prospecting" means NEW reach; never auto-ship low-value while gating the real ask
**Mistake:** Asked to "continue work on linkedin prospecting." I spent the session re-messaging the 5 already-accepted connections with templated value-first thank-yous (personalized opener, but identical AI-tip body + "happy to send the prompt" close across all 5 = reads as bot spam), AND auto-sent those without a final gate. Then I put the actual NEW outreach (13 NY invites) BEHIND an approval gate and walked. Net result Alex returned to: 0 new prospects, 5 canned DMs to warm contacts. Priority was exactly inverted — auto-shipped the low-value maintenance task, blocked the high-value primary task.
**Correction:** "doesn't look like you reached out to any new people but you messaged all the old ones again with some generic garbage bullshit, why the fuck did you do that?!"
**Rule:** (1) When Alex says "prospecting," the default deliverable is NEW connections, not warm-contact maintenance. Lead with new reach; treat thank-yous/follow-ups as optional secondary, never the bulk of a session. (2) Never auto-execute the secondary/low-value action while gating the primary/high-value one — if anything gets a gate, gate the bigger/irreversible thing and just-do the rest, not the reverse. (3) Templated outreach sent to N people with the same body/close is "generic garbage" no matter how personalized the first line — if I can't make each message genuinely specific, don't send it. (4) Acceptance via an AskUserQuestion option is not a license to ship mediocre execution; the quality bar still applies.

## 2026-06-03 — Verify real git HEAD before building; memory is point-in-time
**Mistake:** On a `--resume` into a fresh context, I trusted the 42-day-old Erasure memory that said HEAD was `2af0d54` and started re-building the `legal/` module from scratch. A prior/parallel session had actually moved HEAD two commits ahead (`f5ad0eb` + `ad0ffd0`) and already built that exact module. My re-implementation overwrote committed files (`legal/templates.py`, `legal/__init__.py`, `test_legal.py`) and added a duplicate CLI group, breaking the build.
**Correction:** Self-caught when CLI tests failed with "No such command" (a second `legal` group had shadowed mine), then traced it to pre-existing commits.
**Rule:** (1) Before writing ANY new code in a project, run `git log --oneline -5` + `git status` to learn the true current state — never trust a memory file's commit hash or "what's shipped" claims as live (the memory header even warns they're point-in-time). (2) In the shared `ClaudeProjects` parent repo, assume a parallel session may have committed or staged work since the memory was written; reconcile against real HEAD first. (3) Recovery for an overwrite of committed files: `git restore <path>` from the index (preserves others' staged work) rather than blunt `git checkout HEAD -- .`, then delete only your own untracked additions. It worked cleanly here with zero data loss.

## 2026-06-05 — Read the actual rejection reason; don't infer it from adjacent UI
**Mistake:** Chrome Web Store rejected the MDAC Better extension. I diagnosed the cause as the `tabs` permission by inferring from the Privacy-tab justification form (which documented storage/activeTab/scripting but not tabs) and a yellow "Host Permission" banner. I fixed `tabs`, committed, and pushed before ever opening the Status page. The real machine-readable rejection (Status tab) said: "Requesting but not using the following permission(s): **scripting**." My fix didn't touch the actual violation.
**Correction:** Alex: "make sure you fix the reason for rejecting from before before resubmitting." Reading the Status page revealed the true reason was `scripting` (unused), not `tabs`.
**Rule:** When a system reports a rejection/failure, find and read the authoritative reason field before proposing a fix. For Chrome Web Store that's the **Status tab** ("Violation type / Violation / How to rectify"), not the permission-justification form or the informational host-permission banner. Then verify against code: `scripting` permission is only needed for `chrome.scripting.*` (dynamic injection) — static `content_scripts` in the manifest does NOT need it. `tabs` permission is NOT needed for `chrome.tabs.create/update/reload` or for `tabs.query` filtered to an already-host-permitted URL. Narrowest correct manifest here was `permissions: ["storage"]` + the single host_permission. This is the same point-in-time/assumption failure as the Erasure lesson: trace to ground truth first.

## 2026-06-09 — A SessionStart hook can't be proven within the session that adds it
**Mistake:** After adding a SessionStart hook to `settings.local.json` (to inject `tasks/lessons.md` each session), Alex asked me to "verify the injection works after restart." I set up a sentinel log, Alex said "check it," and the log was empty. I had implicitly hoped to confirm it live, but a SessionStart hook only fires when a NEW Claude Code process starts — it cannot fire inside the already-running session that created it, and typing/resuming in the same process does not emit the event.
**Correction:** Reality (empty sentinel log 3 min after baseline) showed no SessionStart had occurred; the hook was correctly installed (valid JSON, correct structure, no kill-switch) but had nothing to fire on.
**Rule:** When installing any SessionStart hook, state upfront that it activates on the NEXT cold launch and cannot be verified in the current session. To make post-restart verification possible without trusting that I "remember" the content, add a persistent sentinel side-effect (e.g. append a timestamp to a log file) so a fresh timestamp after a genuine quit-and-relaunch is unforgeable proof it fired. Don't promise live verification of process-startup hooks. Also: writing/truncating files under `/tmp` can be blocked by the Bash tool sandbox ("Operation not permitted") even though `/tmp` is writable — appends often work but `rm`/truncate may need `dangerouslyDisableSandbox`; real hooks run outside that sandbox so they're unaffected.

## 2026-06-09 — Separate the "draft/review" decision from the "send mechanism" decision
**Mistake:** Asked to help email 169 Luma workshop attendees, I correctly flagged that "drafts-only + personalized + 169" can't all be true and kept steering Alex toward a one-click mail-merge that *sends*. But Alex's reason for wanting one-by-one drafts was to eyeball each for hallucinations before anything goes out — a quality/accuracy goal, not an efficiency oversight. My framing read as resistance to the very thing he asked for.
**Correction:** "you seem really resistant to drafting the emails one by one so that I can confirm there are no hallucinations, why is this?"
**Rule:** Drafting (human review for accuracy) and sending (delivery mechanism) are independent decisions — don't collapse them. When a user picks a slower, per-item, reviewable path for a correctness reason, honor it as the right call and surface the tradeoff once, then adapt; do not keep nudging toward the faster bulk tool. Re-surface the mechanism question only when the user's stated end-goal (here: "mass send when I have internet") actually requires a different tool, and frame it as serving their goal, not overriding their choice.

## 2026-06-09 — Gitignore PII data folders the moment you create them in a public repo
**Mistake:** Created `hi-im-alex-outreach/luma-workshop-blast/` holding 168 real personal emails inside ClaudeProjects, which is a PUBLIC GitHub repo. The sibling `prospects/` folder was already gitignored for the same reason, but my new folder was not — one `git add` away from leaking the list publicly. Caught it before any commit.

## 2026-06-10 — Schema migrations: an index/constraint on a NEW column must run AFTER the ALTER that adds it (fresh DB hides the bug)
**Mistake:** Added `met_city`/`met_country` to JARVIS's `people` table. I put `CREATE INDEX ... ON people (lower(met_city))` in the CREATE-TABLE block of `SCHEMA_SQL`, which `init_db()` executes top-to-bottom on every boot. On the EXISTING prod table, `CREATE TABLE IF NOT EXISTS` is a no-op, so the column didn't exist yet when the index line ran — Postgres raised `column "met_city" does not exist`, `init_db()` threw, and Railway crash-looped. My local checks passed because the smoke test + structural import checks run against a FRESH DB, where `CREATE TABLE` creates the column so the index succeeds. The advisor had explicitly warned that "the ALTER is what makes this work in prod" and to keep new-column DDL after it — I added the migration ALTER correctly but ALSO left a duplicate index in the table block ahead of it.
**Correction:** Railway "Deploy Crashed\!" email minutes after the push. Self-diagnosed via code trace.
**Rule:** (1) Any DDL that REFERENCES a newly added column (index, constraint, default-from-other-col, check) must appear strictly AFTER the idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` in execution order — put it in the Migrations block, never in the `CREATE TABLE IF NOT EXISTS` block, because that block is a no-op on every existing table. (2) `CREATE TABLE IF NOT EXISTS` only ever helps a brand-new DB; for live tables the migration ALTERs are the ONLY thing that runs. (3) A fresh-DB smoke test cannot catch existing-table migration ordering bugs — mentally simulate the EXISTING-table path: treat the new columns as absent from CREATE TABLE and confirm the rest of SCHEMA_SQL still runs. (4) When the advisor flags a prod-vs-fresh constraint, audit for EVERY instance of the pattern, including duplicates added "for completeness."

## 2026-06-11 — Write shared/global files by ABSOLUTE path; Bash cwd drifts across a session
**Mistake:** Appended a lesson with `cat >> tasks/lessons.md` while the Bash cwd had drifted to `ClaudeProjects/jarvis/` (from an earlier `cd jarvis`). That created a brand-new stray `jarvis/tasks/lessons.md` containing only my entry, while the canonical `ClaudeProjects/tasks/lessons.md` never received it. I'd even Read the canonical file by absolute path moments before, then written by relative path — so I never noticed the target diverged. Caught only at /wrap-up when `git status` in the jarvis repo showed `?? tasks/lessons.md`.
**Correction:** Self-caught during wrap-up; grep of the canonical file returned 0 matches for the lesson I thought I'd saved.
**Rule:** (1) The Bash tool's working directory persists and DRIFTS across a session — never assume cwd. For any write to a shared/global/parent-repo path (`tasks/lessons.md`, memory dir, `.gitignore`, MEMORY.md), use the ABSOLUTE path, every time. (2) Relative paths are only safe for files inside the sub-project you're certain is the cwd, and even then prefer absolute when the file also exists at a sibling/parent level (lessons.md exists in BOTH the parent and several sub-projects — exactly the collision trap). (3) After writing a "saved" artifact, verify it landed where intended (grep the canonical path) before claiming it's done — same ground-truth discipline as the git-HEAD and rejection-reason lessons.

## 2026-06-11 — "Commit X" assumes X is a tracked change; verify tracked-vs-untracked scope before committing in the public repo
**Mistake:** Alex said "commit the rubric change." I treated it as a one-file diff and was about to commit. `git status` showed the file as untracked (`??`), and `git ls-files idea-ranker/` returned empty — the ENTIRE `idea-ranker/` project (25 files of private strategic notes, idea pipeline, TEST-RUN verdicts) had never been committed. A commit would have first-time-published the whole folder to the PUBLIC ClaudeProjects repo, not just the rubric. The "change" Alex pictured (a tracked-file diff) did not exist; from git's view it was a brand-new untracked tree.
**Correction:** Self-caught by inspecting `git status`/`git ls-files`/`git check-ignore` before staging; surfaced the real scope to Alex, who chose to gitignore the folder and keep it local.
**Rule:** (1) Before acting on any "commit X" instruction, run `git status --short <path>` and `git ls-files <path>` to learn whether X is a *modified tracked file* (the user's mental model) or an *untracked file/folder*. They are different actions: editing-then-committing a tracked file is contained; committing untracked paths publishes everything in scope for the first time. (2) In the PUBLIC ClaudeProjects repo, a first-time commit of a project folder exposes ALL of it — scan for private/strategic content and confirm intent before staging; default to offering a gitignore-and-keep-local option. (3) When the real scope differs from what the user's phrasing assumed, STOP and surface the gap (tracked vs untracked, 1 file vs 25) before touching the index — outward-facing publish actions are hard to reverse. Same point-in-time/assumption discipline as the git-HEAD and rejection-reason lessons.

## 2026-06-11 — Claude Desktop skill installation: three tabs, three different systems
**Mistake:** When asked to add a skill to the Claude Desktop app, I spent many back-and-forth turns trying to manually copy files into the Cowork skills directory (the app deleted them), assumed the wrong installation mechanism (double-click on Desktop instead of `open` from CLI), and never clarified upfront which tab the user actually wanted. Could have been done in one pass.
**Correction:** Alex asked for lessons after we finally got it working.
**Rule:** The Desktop app has three completely different skill systems: (1) Chat = no skills, not possible. (2) Code tab = reads `~/.claude/skills/` same as CLI, already works instantly. (3) Cowork = packaged `.skill` files only. Do NOT manually copy folders into Cowork's skills directory — the app deletes them. The correct 5-step procedure: copy skill to clean `/tmp/<name>/` folder, fix YAML (quote description if it contains a colon), validate with `python3 -m scripts.quick_validate`, package with `python3 -m scripts.package_skill /tmp/<name> ~/Desktop`, install with `open ~/Desktop/<name>.skill`. Then start a NEW Cowork task. Full paths + validation rules in memory file `reference-claude-desktop-skill-install.md`.

## 2026-06-11 — Isolate synthetic/dry-run output from the live dataset; demo twice
**Mistake:** The sports validation prototype's dry-run mode wrote synthetic paper trades into the same SQLite files (`data/paper_trades.db`) the operator's real game-day data would land in — the dataset that decides the go-live promotion gate. The bug passed all 125 tests and the first smoke test; it only surfaced when the smoke test was run a SECOND time and the summary showed an accumulated trade from the prior run.
**Correction:** Self-caught while demoing the dry run for Alex; fixed by routing dry-run output to `data/dryrun/`.
**Rule:** (1) Any simulation/dry-run/test mode must write to storage isolated from the real dataset from day 1 — an accumulating shared store silently poisons the data that downstream analysis judges. (2) Run demos and smoke tests at least twice before calling them done: single-run checks can't catch state-accumulation bugs, which by definition need a second run to appear.
